# ADR-012：以照片集组织项目

- 状态：已接受
- 日期：2026-10-23
- 关联：ADR-003 文档模型、IPC 契约「应用与项目」

## 背景

早期模型把每张照片当作一个独立项目：导入、打开、重命名与删除都以照片为单位，最近项目列表就是照片列表。用户期望的是相反的层级：**一个项目是一组照片**，底部列表只展示当前项目的照片，切换项目即切换照片集；新建项目应先命名照片集，再加入第一张照片。

这需要在不丢失既有用户数据（P1023649、meta-source）的前提下引入照片集，并保持每张照片仍是非破坏编辑、独立保存的文档。

## 决策

1. 不引入独立的 `collections` 表。照片集身份与名称直接存在每张照片的项目记录与文档上：`collection_id` / `collection_name`（SQLite `projects` 表 + `ProjectDocument`）。
2. 数据库 schema 升到 v2：打开旧库时检测列是否存在，缺失则 `ALTER TABLE projects ADD COLUMN`，并用 `UPDATE ... SET collection_id = id, collection_name = name` 把每张旧照片迁移为单张照片的照片集。索引在迁移后创建，避免旧库在列不存在时建索引失败。
3. 文档 schema 升到 13：旧 JSON 缺少集合字段时，`normalized()` 回填为项目自身 id/name，与数据库迁移结果一致；下次保存写回 schema 13。
4. 导入接口只在“加入哪一组”上扩展：`collectionId` 表示加入现有照片集（服务端校验集合存在），`collectionName` 表示新建照片集（规范化名称，最长 120 字符），两者都省略时这张照片自成一个照片集。照片本身仍然创建独立的项目记录、资产目录与文档。
5. `list_collections` 从 `list_projects` 的摘要按 `collectionId` 分组：封面与默认打开的照片取最新一张，`photoCount` 为组内照片数。列表不单设集合表，因此不存在空照片集；删除集合内最后一张照片即移除该集合。
6. 前端把“项目 / 照片”两个层级落实到界面：欢迎页与顶部「项目」菜单列出照片集；底部照片集条只筛选当前 `collectionId` 的照片；顶部标题显示“照片集 / 照片”（同名时省略重复部分）；「新建项目」先命名集合再选第一张照片，「添加照片」把新照片加入当前集合。
7. 批量导出不由后端新增命令：前端对当前集合中勾选的照片逐个调用现有 `export_image`，沿用导出格式、质量与各自裁剪后的原尺寸；先提交尚未落盘的调整，重名自动追加序号，并显示逐项进度。切换集合时清空跨集合的选择。
8. `rename_project` 保持照片级语义，不修改集合名称。集合重命名尚未提供界面；如需支持，应在服务层批量更新该 `collectionId` 的数据库行与打开中的文档，而不是只改第一张照片。

## 备选方案

- **独立 collections 表 + 外键**：模型更正规，支持空集合与集合级元数据，但需要重写导入、列表、删除与迁移路径，并回填用户数据；首期收益不足以抵消迁移风险。当前方案在保持既有文档结构的前提下完成层级拆分，未来可平滑引入表而不改变前端契约。
- **前端仅按名称分组**：同名的不同项目会被错误合并，且重命名会拆分照片集，不可接受。
- **把照片集做成虚拟项目文档**：会让“打开照片”和“打开项目”共用同一文档类型，状态、历史与渲染都会混淆。

## 后果

- 优点：用户数据无损升级；照片集与照片的层级清晰；每张照片仍可独立编辑、恢复与删除；无需维护空集合。
- 代价：照片集名称冗余存储在每个成员上；集合级重命名/删除需要批量操作（目前删除通过逐张删除照片完成）；集合不能在没有照片时预先存在。
- 旧文档在首次重新保存前，JSON 中可能仍是旧 schemaVersion；载入时会规范化，行为不受影响。

## 验证

- 旧库升级后 `P1023649` 与 `meta-source` 各自成为一个包含 1 张照片的照片集，原图与文档未被改写。
- 新建集合并导入两张照片后，`list_collections` 返回 `photoCount = 2`，底部条只显示这两张；加入其他集合的照片不会混入。
- 从「项目」菜单切换集合后，标题、底部条、当前选中照片与批量导出范围同步切换。
- 删除验证用照片集后，数据库中只剩用户原有的两个项目，项目目录同步清理。
