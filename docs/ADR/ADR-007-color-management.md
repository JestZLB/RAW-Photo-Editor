# ADR-007：ICC 色彩管理输入/输出与广色域

- 状态：已接受
- 日期：2026-10-21
- 关联：架构文档 05、ADR-001、ADR-003、兼容性矩阵

## 背景

工作空间固定为线性 sRGB，但真实照片可能带 Display P3、Adobe RGB 或相机厂商的 ICC 配置。此前解码时直接忽略内嵌配置，等于把广色域文件当成 sRGB 读取，颜色偏灰；导出同样从不写配置，广色域结果无法安全交付。可用的纯 Rust 色彩引擎（iccbake / colorprof / argyll）在当前镜像源不可安装，`lcms2` 需要引入 C 依赖与跨平台构建。

## 决策

1. 自己实现所需的最小子集（`crates/image-core/src/icc.rs`），不引入新依赖：解析 ICC v2/v4 头部与标签表、`rXYZ/gXYZ/bXYZ` 色度列、`curv`/`para`(1..4)/`mntr` 曲线与表格曲线、`desc`/`mluc` 描述。
2. 转换路径固定为：编码值 → 通道 TRC → 配置矩阵到 D50 PCS → Bradford 适配到 D65 → 线性 sRGB。反向用于导出。适配矩阵的逆由代码求解，不使用四舍五入过的公开常量（实测残留 0.6% 偏色）。
3. 只处理 `mntr` + `RGB ` 且带矩阵/TRC 的配置。`mft1`/`mft2`/`lut8`/`lut16`、CMYK、抽象空间等只识别不转换，按 sRGB 处理并在兼容性矩阵中写明，绝不猜测。
4. 转换发生在导入解码阶段：原文件永不改写，缓存预览、会话内解码图与渲染都工作在 sRGB 工作空间。因此 WGPU 路径不需要任何改动。
5. 与 sRGB 足够接近的配置（D65 矩阵误差 ≤0.02 且曲线与 sRGB 一致）判定为工作空间本身，像素按位不变，避免为无意义的配置引入舍入误差。
6. 真实转换过的项目把源配置作为 `kind = "icc"` 资产存在项目目录，文档只记录 `iccAssetId` 与 `colorSpace` 标签（schema 8）。删除项目即清理。
7. 导出提供三档：`srgb` 不写配置（通用约定）、`displayP3` 写入代码生成的 P3 配置、`source` 写回导入时保留的配置。`ExportResult.colorSpace` 报告实际写入值，无源配置时 `source` 回退 sRGB，界面提示差异。
8. TIFF 也写入配置（`image` 会写 `IccProfile` 34675 标签），但它的解码器读不回自己写的 BYTE 数组，因此导入侧对 TIFF 增加直读标签的兜底（`tiff_file_icc` / `tiff_icc_from_bytes`），保证导出再导入仍是同一色彩空间。
9. 浏览器演示模式不具备 ICC 读写能力，固定按 sRGB 报告与导出，广色域选项在演示模式下禁用。

## 后果

- 优点：广色域照片不再被误读；导出结果带正确标注，其他软件能还原显示；零新增依赖，纯 Rust 且可单测。
- 代价：只覆盖矩阵/TRC 配置， perceptual/saturation 渲染意图与带 A2B 表的打印机配置不支持；超出 sRGB 的像素在导入时截断，无法逆向恢复（导出"原图配置"只能还原未截断的部分）。
- 自研实现需要持续用真实配置回归验证；当前以合成配置往返与已知空间判定作为防线。

## 验证

- 合成配置往返：sRGB 判定为工作空间且像素按位不变；P3/Adobe 判定正确；白点保持；P3→sRGB→P3 在 8 bit 内 ≤2 级误差；截断/损坏/非 RGB 输入被拒绝或原样跳过。
- 编解码闭环：带 P3 配置的 PNG/JPEG/TIFF 解码后像素被重映射；TIFF 经标签直读兜底后同样识别为 Display P3。
- 服务端：导入广色域照片后 `colorSpace = "Display P3"`、`hasSourceProfile = true`；`source` 导出回到原配置与原值；`displayP3` 导出写入配置；TIFF 广色域写入 34675 标签，重新导入仍识别为 Display P3。
- 真机：Display P3 样片导入后面板显示来源与转换说明，导出窗口三个色彩空间卡片可用状态正确，导出文件的 `iCCP` / `APP2` 内容与预期配置逐字节一致。
