# ADR-004：预览后端、缓存与 WGPU 迁移策略

- 状态：已接受（CPU 基线；WGPU 子集已接入）
- 日期：2026-10-21
- 关联：架构文档 04 / 09

## 背景

首期需要可测、可回放的像素基线。WGPU 在目标 Windows 设备与 WebView2 环境中的性能、驱动兼容性与设备丢失行为尚未验证，不能作为唯一执行路径。

## 决策

1. 保留 **CPU 参考后端** 作为正确性基线；WGPU 为可选加速路径，初始化失败、无适配器或不支持的图层组合自动回退。
2. WGPU 第一阶段覆盖：基础照片、调色（清晰度/锐度必须为 0）、裁剪、AI 结果图层、不透明度与混合模式。含活动人像图层、局部细节调整或活动蒙版（画笔/自动肤色）时回退 CPU。
3. 预览使用缩放代理图（默认最长边 1600），导出使用原始分辨率重新渲染；预览缓存键包含项目、revision 与 maxDimension。
4. 预览文件写入缓存目录并以路径 + Tauri asset protocol 提供给前端；IPC 不传输像素或 Base64 大图。
5. 同时最多保留 3 个打开项目的解码源图，全分辨率缓存总预算 **256MB**，超出按最近最少使用释放；单张超过 128MB 的源图不进入缓存（调用方持有的 Arc 仍可用于当前操作），避免 100MP 图长期占用数百 MB。
6. 后续 WGPU 工作：
   - 人像图层 GPU 化与清晰度/锐度的多通道模糊；
   - 设备丢失恢复、显存预算、高分辨率分块；
   - 在目标 Windows 硬件上记录驱动、显存和延迟基准。
7. `PreviewResult.backend` / `ExportResult.backend` 返回实际使用的 `wgpu`、`cpu` 或 `cache`，前端状态栏据此显示，不得用能力开关冒充实际后端。
8. 预览缓存自回收：每次成功渲染后按「项目 + 尺寸」只保留最近 2 个 `render-r{revision}-d{dim}.png`，其余立即删除。文件名里的 revision 就是排序键（一次连续拖动内 mtime 会并列，不可靠）；设置页的全局 `clear_render_cache` 保留为手动兜底。
9. CPU 合成跨图层复用一块 scratch 缓冲（`LinearImage::copy_from`），不再每层 `clone()` 整幅线性图。线性图 16 B/像素，1 亿像素导出时每层省约 1.6 GB 峰值；每层仍从"已合成的画面"起步，语义与逐层克隆完全一致。无蒙版、正常混合且不透明度 100% 的调色/人像图层直接在该缓冲上就地应用，常见单图层文档完全不分配 scratch；有蒙版/羽化/混合模式时仍走克隆+合成路径。
10. 解析后的 `.cube` 按资产 id 缓存在服务里（上限 4 个，超出即清空）。实测 48³（约 3 MB 文本）解析 60 ms、64³ 约 110 ms，逐帧重解析会直接吃掉预览预算；资产 id 每次导入都是新 UUID，因此缓存不存在读到旧内容的可能。
11. 裁剪工具通过 `ignore_crop` 请求完整画面预览（缓存文件名加 `-full` 后缀，仍按 revision/尺寸回收）；旋转在裁剪期间由前端用 CSS 呈现，应用时才由后端一次性旋转采样，避免重复缩放。
12. 人脸模型解析（实测 1.5 ms）不做缓存：成本远低于引入 `OnceLock` 全局状态的价值。
13. 预览的直方图按缓存路径记忆（上限 16 条）。缓存命中时原本要重新解码整张 PNG 才能填 4×64 个分箱；路径里已经包含 revision 与尺寸，因此缓存项不可能描述别的像素。
14. 自动校正、白平衡吸管、人脸检测与五官区域分析只读最长边 1600 的源图代理，不再为一次 256 分箱统计或 640px 人脸检测解码全分辨率照片；代理缺失时回退全图并缩小。分析结果本来就是归一化坐标或参数，代理尺寸不影响语义。
15. 预览中间渲染的过采样上限为 4096（若请求尺寸更大则按请求值），避免极小裁剪为了 1600px 预览生成 8192px 的线性中间图；线性图 16 B/像素，8192px 会放大到数百 MB。GPU 的源纹理代理使用同一上限，导出（无 maxDimension）仍上传完整源图。结果裁剪后若仍大于请求尺寸，再做一次 Lanczos 下采样，保证预览不超过 maxDimension。
16. 1600px 及以下的预览，在裁剪区域足够大（按代理像素所需的 5% 容差判断）时直接解码磁盘上的 1600px 源图代理，并把像素级裁剪矩形等比缩放到代理坐标后再渲染；微小裁剪与 2048px 预览仍使用全图，以保留细节。这样常见的全幅调色预览不再为 1600px 结果解码 100MP 原图。
17. 解码后的 1600px 代理按项目缓存在内存（`OpenProject.proxy`，带 asset id 校验）。拖动滑块时每帧重新解码 PNG 的成本高于这一档渲染本身；一个 RGBA8 代理约 10 MB，而同时最多 3 个打开项目，因此额外占用有上界。代理随会话释放，`write_source_previews` 重写磁盘代理时立即失效，源图资产 id 变化时不会被误用。
18. 前端采用双档预览：拖动滑块时请求 900px，静止约 420ms（或提交编辑）后回到设置档位（1200/1600/2048）。两档都在 1600px 代理的覆盖范围内，因此共享同一份解码缓存；缓存键含尺寸，两档互不覆盖。交互档只改变预览清晰度，不改变最终像素与导出结果，且静止后必定请求高清晰档，避免停在低分辨率。高频写入走 `update_layer_params_meta`，其响应不含图层负载。

## 后果

- 优点：兼容文档获得本地 GPU 加速，同时正确性仍由 CPU 基线和容差回归保证。
- 代价：GPU 覆盖仍是子集；人像与清晰度/锐度文档回退 CPU；设备丢失和显存预算尚未实现。

## 验证

- CPU/GPU 对同一调色文档的最大通道误差 ≤ 6；带裁剪与 AI 混合图层的误差 ≤ 12。
- 活动人像图层会返回 GPU unsupported 并回退 CPU；非零裁剪角度同样回退 CPU。
- 缓存命中返回相同路径；新 revision 不命中。
- 缓存命中返回的直方图与首次渲染逐分箱一致（真机 + 集成测试），且 `durationMs = 0`，不再为分箱解码整张 PNG。
- 连续 8 次 revision 渲染后，预览目录内 `render-*` 不超过 2 个，且当前显示的那张必然保留（`render_previews_are_pruned_as_revisions_advance`）。
- 两层调色文档（+3 EV @50% 不透明度叠 −3 EV）与手工合成参考逐像素一致；去掉 scratch 复位后该断言失败，说明它真的能抓到 scratch 复用缺陷。
- 真机：48³ LUT + 两层调色在示例人像上渲染，像素随每层变化、缓存命中 `durationMs = 0`；渐变叠加层在画笔工具切换并再次缩放后端点坐标仍跟随画布（见 `screenshots/gradient-overlay-after-brush.png`）。
- 导出尺寸/色彩与预览一致（分辨率不同）。
- 无 GPU 环境下所有功能可用。
